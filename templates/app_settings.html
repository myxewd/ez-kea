Kea 3.x installed from ISC's own packages ships no keactrl at all — pick "Control socket" there. It sends config-reload straight to the daemon, needs no external binary, and is the only strategy that reports whether the reload actually succeeded. It requires a unix entry under the daemon's control-sockets.
Minimal Kea Docker images often don't ship /etc/kea/keactrl.conf, which keactrl reload requires — "Docker container SIGHUP" covers those.
Kea HTTP API pushes the configuration to the running daemon over its own HTTP/HTTPS control socket, in two steps: config-test (Kea's own parser judging this exact document) and only then config-set. Nothing is applied if the test is refused, and the file on disk stays the source of truth, so a restart lands on the same configuration. Needs an http (or https) entry under the daemon's control-sockets — Kea 2.7.2 and later. This is never guessed; pick it explicitly.
The daemon's HTTP/HTTPS control socket, e.g. http://127.0.0.1:8000/. Leave blank to use the http/https entry in the daemon's control-sockets (defaults 127.0.0.1:8000, and [::1]:8000 for DHCPv6). Set it when the listener is not described there — another host, or a port published out of a container.
Kea 3.x refuses an unauthenticated HTTP control channel at startup ("Unsecured HTTP control channel"), so configure basic auth on the daemon (user-file/password-file — a clear-text password in Kea's own config is refused too) and set KEA_HTTP_USER/KEA_HTTP_PASSWORD in EZ-KEA's environment. Credentials are deliberately environment-only, never a field on this page. Client certificates are not supported, so an HTTPS listener must set cert-required to false.
